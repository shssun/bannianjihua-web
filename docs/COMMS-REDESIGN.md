# 沟通方式重新设计（提案）

> **触发**：老板 2026-10-14 ——「花点时间好好考虑一下你和 trae 的沟通方式，不要再持续的一遍又一遍的互相抢夺一个文件的许可权，然后修改的内容又返工之类的」。
> **状态**：**提案，待老板拍板**。拍板前不动现有协议 / 脚本 / 清单。
> **本文只谈"怎么沟通"，不谈任何功能任务。**

---

## 0. 一句话

**现在的做法是「共享可变文档」—— 同一份任务的信息存在两个地方，靠规则去缝。缝一次就多一层耦合。**
**改法是「只追加事件流」—— 谁也不改任何已写下的东西，「抢夺许可权」在物理上不再可能。**

打个比方：现在是两个人共用一块白板，各写各的区域，还要规定"你只能写右半边、我不能擦你的字"。只要有人手滑整块重写，对方的字就没了 —— 所以必须配一个监工（`check`）站在旁边。
改法是换成**两本各自独立的本子，而且只准往后翻页写、不许涂改**。监工就不需要了。

---

## 1. 病根：不是规则不够，是"共享状态"本身

### 1.1 状态是**存储**的 → 必然要回答"谁说了算"

一个任务的状态（`todo` / `doing` / `done` / `verified`）现在物理上存在**两个地方**：BACKLOG 的 `verdict`/`status`、EXEC-REPORT 的 `status`。于是必须有**合成规则**（协议 §7.3.1 那 4 行 if-else）把它们缝起来。

有合成就有优先级 → 有优先级就有"谁说了算" → **这就是老板说的"抢夺许可权"**。它不是谁脾气坏，是**结构逼出来的**。

### 1.2 两个文件靠**复制的字符串**关联 → 必然要人工同步

EXEC-REPORT 第 19 行白纸黑字要求：「`id` 必须与 BACKLOG 完全一致（`check` 会交叉校验）。**标题请与 BACKLOG 保持一致**」。

即：`id` 和**标题**这两个东西，在两个文件里各存了一份，靠人肉保持一致。这是典型的"外键靠手工同步"——所以才会长出**幽灵 id 检测**、**标题一致性检查**这些校验。

### 1.3 任务定义是**活的** → 我改一下，它正在做的活就作废

`spec` / `acceptance` 归我方，我随时能改。但它可能**正在按旧 spec 干活**。我 21:03 改一次，它 20:54 的成果就"过期"了 —— **这是返工的第二大来源**（第一大来源是覆盖）。

### 1.4 为什么每个补丁都让耦合更深

```
补丁①「状态拆到两个文件」  → 引入 id 关联
补丁②「交叉校验」          → 因为①的关联会错
补丁③「纠错性恢复 §7.3.0」 → 因为②发现"我方会误碰它的文件"（它本来就该不该碰？）
补丁④「reject 闭环」        → 因为①之后"打回"要跨两个文件走
补丁⑤「staleDoing 检测」    → 因为④又产生了新的漏改状态
```

**每一条都在补偿①带来的问题，而①本身没动。** 这就是"一遍又一遍"的机理：**在错的前提上打补丁，补丁必然生补丁。**

### 1.5 已被实际发生的 4 次事故（不是假想）

| # | 事故 | 根因 |
|---|---|---|
| 1 | Trae 在 T-009 的 evidence 里自述：**「实施期间并行会话两次全量写回覆盖 doing 标记」** | 两个写者 + 整文件写回 |
| 2 | 我方 21:03 迁移时**把 T-021 从 `doing` 误改成 `todo`** | 我给的是**快照**，而文件是**活的** |
| 3 | `BACKLOG.md` 头部说明**仍是旧契约**，与 §7.3 冲突，而执行方每次都先读它 | 门面文字与契约**分离在两处** |
| 4 | 我方 19:31 的 `git push` **带上了 Trae 未复核的两个提交** | 交接面靠"人记得"而不是靠结构 |

## 2. 新设计：只追加事件流

### 2.1 三个文件、三个写者、零重叠

| 文件 | **唯一写者** | 内容 | 写的方式 |
|---|---|---|---|
| `docs/TASKS.md` | **我方** | 任务卡：`## T-024` 块（`spec` / `acceptance` / `priority` / `area` / `depends` / `size`） | **只追加**；写出即冻结 |
| `docs/OWNER-LOG.md` | **我方** | 我方事件流（派活 / 验收 / 打回 / 暂缓 / 作废） | **只追加** |
| `docs/EXEC-LOG.md` | **执行方** | 执行方事件流（认领 / 完成 / 阻塞 / 备注） | **只追加** |

**注意 `TASKS.md` 里没有 `status`、没有 `evidence`、没有轨迹** —— 状态**不再被存储**（见 2.3）。

### 2.2 三条铁律（原 §6 的 12 条例律可删掉大半）

1. **只追加，不修改。** 任何一方都不得删除、改写、重排已有行。
2. **不写别人的文件。** 我方只碰 `TASKS.md` + `OWNER-LOG.md`；执行方只碰 `EXEC-LOG.md`。
3. **任务 id 单调递增、永不复用。** 改需求 = 追加一张**新卡**，旧卡在日志里写一条 `supersede`；**绝不原地改旧卡**。

### 2.3 状态不再是"存的"，而是"算的"

```
任务状态 = 两条日志里所有提到该 id 的事件中，时间戳最新的那一条
```

一行一条事件，格式固定为：

```
<ISO8601-UTC> | T-012 | <verb> | k=v | k=v | ...
```

| verb | 谁写 | 推导出的状态 |
|---|---|---|
| `dispatch` | 我方 | todo（派发） |
| `hold` | 我方 | todo（暂缓，别领） |
| `claim` | 执行方 | doing |
| `blocked` | 执行方 | blocked |
| `done` | 执行方 | done（**等我方验收**） |
| `verify` | 我方 | **verified（终态）** |
| `reject` | 我方 | doing（打回，等重做） |
| `supersede` | 我方 | 旧卡作废（指向新 id） |

**推导规则只有一句：「看最后一条事件」。** 没有优先级表、没有合成函数、**没有"谁说了算"** —— 因为每条事件都带时间戳，**后写的赢**。这是自然次序，不是一条需要记忆的规则。

### 2.4 一次完整的示例（T-012 走完一生）

`docs/EXEC-LOG.md`（执行方写）：
```
2026-10-15T02:30:11Z | T-012 | claim | note=开始实现互评走廊
2026-10-15T03:44:02Z | T-012 | done  | commit=abc1234 | files=src/pages/PeerCorridor.tsx | checks=tsc:0,build:0 | note=...
```

`docs/OWNER-LOG.md`（我方写）：
```
2026-10-15T04:10:33Z | T-012 | verify | result=4/4 | note=真浏览器复验：两账号互评闭环通过
```

→ 状态 = **verified**（最后一条事件是 `verify`）。全程**没有谁修改过任何一行**，也没有谁碰过对方的文件。

### 2.5 打回：3 步变 1 步

| | 现在 | 新设计 |
|---|---|---|
| 我方打回 | 加 `reject` 轨迹（不改 verdict）+ 执行方须 `retract` + 改回 `doing`（**跨两文件、三步**） | 我方 append **一行** `reject` → 状态自然是 doing |
| 执行方重做 | 必须"撤销"自己之前的声明 | 直接再做、再 append 一行 `done`。**不需要撤销任何东西**（它写下的历史是对的，只是被后续事件覆盖了含义） |

## 3. 前后对比

| 维度 | 现在 | 提案 |
|---|---|---|
| 信息与写者 | 任务信息**交叉存储**在两个文件 | **一一对应**：一块信息只有一个家 |
| 写的方式 | **覆盖**（可以改任意行） | **只追加**（不许改任何已有行） |
| 状态 | **存储**（两处）+ 合成规则 | **推导**（看最后一条事件） |
| 两文件关联 | 靠 `id` + **标题**字符串人工同步 | 事件里写 id；**不做一致性校验**（只需单向提示） |
| 指令下发 | BACKLOG 顶部**"活的"指令区块**（每轮重写） | OWNER-LOG 里**追加一行** `hold`/`dispatch` |
| 门面与契约 | 头部说明 + 协议 §7 两处，会漂移 | **同一处**（规则写在 `TASKS.md` 顶部，与卡片同文件） |
| 冲突可能 | **有**（已实际发生 4 次） | **物理为零**（各写各的 + 只追加） |
| 纪律条数 | 12 条（§6） | **3 条**（2.2） |
| 校验器 | 1444 行，一半在"替两个写者守边界" | **~300 行，只查一件事：本次改动是否纯追加** |

## 4. 三个返工来源，逐个消除

| 返工来源 | 为什么会返工 | 新设计为什么不会 |
|---|---|---|
| **覆盖** | 两个写者对同一文件产出整文件新版本 | 各写各的文件；且只追加 → **无任何一行会被别人重写** |
| **spec 原地改** | 我改了定义，它按旧定义做的活"过期" | 卡冻结：改需求 = **新卡**；旧卡 `supersede` 指向新卡，**已做产物显式继承**，不白做 |
| **打回重置** | `reject` → `retract` → `doing` 跨两文件三步，中途又可能被覆盖 | `reject` 就是一行；它直接继续。**历史是只追加的，谁也删不掉** |

**一句话：新设计里，"返工"这件事没有发生的位置。**

---

## 5. 校验器瘦身

`scripts/backlog.mjs` 现在 1444 行，其中**至少一半**在替两个写者守边界：交叉校验、幽灵 id、双文件必填键、有效状态合成、reject 闭环、纠错性恢复、staleDoing……

新校验器**只需要三件事**，而且**全是单向的**（不涉及两个写者协调）：

1. **本次改动是否为纯追加** —— 对三个文件跑 `git diff`，若删除或改写了任何**非空行** → 告警。
2. **事件行格式合法** —— ts / id / verb 三段 + `k=v` 对；verb 在白名单内。
3. **`TASKS.md` 的 id 唯一且单调递增**；`verify` 之后同 id 不得再出现事件。

**规则 1 是唯一需要"守"的东西，而它是单向的**（谁违规都指向同一个文件，不产生"你该改还是我该改"的僵局）。

## 6. 迁移：一次切换，之后永久免疫

### 6.1 步骤（全部由我方执行，执行方只做一次动作）

1. 我方从现有 BACKLOG/EXEC-REPORT **生成**三个新文件的**初始内容**（只读旧文件，不删不改）。
2. 在 `TASKS.md` 顶部宣布**通道切换时刻**，并在 `OWNER-LOG.md` 记一条 `cutover`。
3. **执行方只需做一个动作**：下一轮起，把事件写进 `EXEC-LOG.md`（新文件），别再动 `EXEC-REPORT.md`。
4. 我方**观察一轮**，确认它切过来了 → 之后**再也不需要任何"协调"**。
   旧文件改名为 `docs/archive/EXEC-REPORT.md` 留作历史（不删，可追溯）。

> ⚠️ **这一次切换是不可避免的一次协调，但它也是最后一次。** 现状则是**每轮都要协调**。

### 6.2 代价与风险

| 项 | 评估 |
|---|---|
| 工作量 | 我方约 1~1.5 小时（写 3 个新文件 + 简化 `backlog.mjs` + 精简 `AI-HANDOFF.md` §6/§7/§8） |
| 执行方成本 | 只改**写入目标文件名**一个动作；事件格式比现在的 `evidence` 行**更简单** |
| 主要风险 | **执行方没有及时切过来**，两边都写 → 但即便发生，也**只是"新事件写在旧文件里"，不会丢数据**（因为旧文件也还在）；我方下一轮在 `OWNER-LOG` 追加一条提醒即可 |
| 不可逆性 | 低。旧文件全保留，随时可回退 |

### 6.3 旧文件的下场

| 文件 | 处理 |
|---|---|
| `docs/BACKLOG.md` | 内容迁入 `TASKS.md` + `OWNER-LOG.md` 后归档 |
